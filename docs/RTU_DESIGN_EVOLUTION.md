# RTU 设计演进记录

本文记录 RTU 模块从“一个类完成全部工作”演进为当前多角色、状态明确、
strand 串行化的过程。重点不是代码行数，而是每次修改解决了哪类边界问题，
以及为什么没有继续引入更重的通用框架。

## 1. 初始阶段：单个 RtuConnection

最初的 `RtuConnection` 同时承担：

- 串口打开和参数配置。
- CRC、帧长度和请求/响应解析。
- 手动帧发送和接收。
- 主站事务、重试和响应匹配。
- 从站请求接收、Mapping 处理和响应发送。
- RS485 配置。

这种方式在只有一个专用线程、固定调用顺序时容易理解。但随着功能增加，
同一个对象开始允许以下调用交错：

```text
手动接收 + 主站事务
主站事务 + 从站服务
发送请求 + 清空输入
取消操作 + 正在投递的读写
关闭对象 + 尚未返回的回调
```

为了描述这些组合，内部逐渐出现多个布尔变量、队列、定时器和取消标志。
这些变量单独看都合理，组合起来却很难证明没有矛盾。

主要问题不是“只有一个类”，而是这个类没有一个稳定、单一的状态来源。

## 2. 第一次重构：按角色拆分

RTU 被拆成三个公开角色：

| 类型 | 职责 |
| --- | --- |
| `RtuConnection` | 手动调试，收发完整 RTU ADU |
| `RtuMaster` | 事务 FIFO、重试、响应匹配 |
| `RtuSlave` | 从站服务循环、地址过滤和 Mapping |

同时新增：

- `detail::SerialTransport`：串口打开、读写和定时器。
- `detail::rtuCodec`：CRC、帧长度、请求和响应匹配。
- `rtuTypes.h`：串口、主站、从站和帧类型等公共配置。

这是一次典型的职责分离，按职责而不是按代码调用顺序拆分模块。

## 3. 删除通用 Operation / Job 队列

一次中间设计曾在串口层建立通用 Send/Receive/Clear 任务队列，并让主站、
从站和手动操作共享同一调度器。

这个设计可以复用底层收发，但产生了新的复杂度：

- 主站已经有事务队列。
- 从站本来只有一个服务循环。
- 串口层再建立一层队列，会让取消、关闭和代次判断跨两层进行。
- 一个“已投递但尚未启动”的操作很难被正确取消。

最终保留的结构是：

```text
RtuMaster -> 事务队列 -> SerialTransport
RtuSlave  -> 服务循环 -> SerialTransport
RtuConnection -> 单个手动操作 -> SerialTransport
```

`SerialTransport` 同时只持有一个读或写。时序由拥有串口的主站或从站负责，
不再建立通用虚函数 Operation 体系。

设计判断：

- 组合优于继承。
- 串口传输可以复用，但主站事务循环和从站服务循环不应被强行抽象成同一种任务。
- 只有一套实际调用方时，不为未来假设建立虚基类或命令类层级。

## 4. 帧长度和协议判断独立

`rtuCodec` 只处理纯数据：

- CRC 校验。
- RTU ADU 最大长度。
- 请求/响应长度计算。
- 异常码和广播功能码判断。
- 响应与请求地址、功能码、数据量和写回显匹配。

协议函数不访问串口、不启动定时器、不修改业务状态，因此可以：

- 不启动 `io_context` 直接测试坏帧。
- 用固定字节样本复现问题。
- 单独修改功能码支持范围。
- 不依赖主站或从站生命周期。

这是模块中最适合保持纯函数的部分。

## 5. strand 状态封闭

当前异步状态统一在串口 strand 上修改：

- 当前底层操作。
- 主站事务队列。
- 从站服务状态。
- 定时器。
- 取消代次。
- 关闭等待者。

跨线程入口只负责投递完整请求：

```cpp
asio::dispatch(strand, [state, request, handler]() mutable
{
    state->enqueue(std::move(request), std::move(handler));
});
```

进入 strand 后，内部函数直接修改状态，不再层层 `post()`。

这个思路接近 Actor 的状态封闭，但没有引入 Actor 框架。它的核心约束是：

```text
同一份异步状态只能由一个执行序列修改。
```

## 6. 取消代次

仅检查“当前是否有活动操作”不够，因为操作可能已经投递、尚未在 strand 上登记。

因此增加了两类代次：

- 主站 `cancellationEpoch`。
- 从站 `serviceEpoch`。
- 串口 `submissionEpoch`。

提交操作时记录代次，真正启动前再次比较。取消或关闭会使旧代次失效。

这解决了两类问题：

- `asyncTransaction()` 后立即 `cancel()`，请求仍被发送。
- `asyncServe()` 后立即 `stopServe()`，旧读操作随后启动。

代次只用于拒绝旧提交，不替代 I/O 完成回调，也不引入通用任务对象。

## 7. 帧间等待

RTU 的正常请求和响应之间也必须满足总线静默间隔。

`SerialTransport` 维护：

```cpp
Clock::time_point nextTransmit;
```

规则：

- 收到请求或响应字节后更新 `nextTransmit`。
- 发送完成并排空后更新 `nextTransmit`。
- `beginWrite()` 发现当前时间早于 `nextTransmit` 时先等待。
- 发送排空保护仍然保留，不能替代接收后的静默等待。

这使主站下一笔事务、从站正常响应和重试发送都经过同一套帧间等待。

## 8. 手动帧类型

请求和响应不能对所有功能码都靠内容自动区分。例如请求第三字节可能是地址高位，
响应第三字节通常是数据字节数。

因此手动接口显式接受帧类型：

```cpp
manual.asyncAwaitRawMessage(RtuFrameType::Request, handler);
manual.asyncAwaitRawMessage(RtuFrameType::Response, handler);
```

原响应接收重载保留为兼容便利接口。

## 9. 串口状态

串口使用明确状态：

```cpp
enum class SerialState
{
    Closed,
    Open,
    Closing
};
```

状态规则：

| 状态 | 允许的操作 |
| --- | --- |
| `Closed` | 修改配置、打开 |
| `Open` | 读写、取消、请求关闭 |
| `Closing` | 等待旧 I/O 和关闭清理完成 |

当前 `open()` 是同步的，所以没有单独的 `Opening` 状态。只有在未来改成
异步打开时才需要增加。

关闭完成前不能重新打开。只有关闭流程自身能把状态设置为 `Closed`。

## 10. 异步关闭完成边界

三个公开角色都提供：

```cpp
void asyncClose(RtuCompletionHandler handler = {});
```

回调执行时应满足：

- 旧事务或从站服务已经收尾。
- 底层读写已经结束。
- 串口已经关闭。
- `SerialState == Closed`。
- 可以从回调中重新调用 `open()`。

`close()` 作为兼容入口保留，等价于发起关闭但不等待完成。需要确定关闭完成时，
应使用 `asyncClose()`。

多次关闭请求会由串口关闭等待者统一收尾，不会关闭一次却漏掉其他完成回调。

## 11. 服务状态

从站使用：

```cpp
enum class ServiceState
{
    Idle,
    Running,
    Stopping
};
```

状态转换：

```text
Idle -> Running -> Stopping -> Idle
```

`businessPending` 仍作为独立状态，因为业务派发可以排到其他执行器，并且业务返回
不能由普通定时器推断。停止流程会等待已派发业务返回。

从站同态使用 `serviceEpoch` 拒绝：

- 停止前已投递但未启动的服务。
- 关闭后旧回调对新服务的影响。

## 12. 所有权

当前所有权关系：

```text
RtuMaster 拥有一个 SerialTransport
RtuSlave  拥有一个 SerialTransport
RtuConnection 拥有一个 SerialTransport

SerialTransport 持有 State shared_ptr
异步回调持有执行期间需要的 shared_ptr 状态
每笔主站事务持有请求、缓冲区、定时器和完成回调
```

这样做的目的：

- 用户不能通过主站接口绕过事务队列。
- 串口关闭职责只属于传输对象。
- 回调可以在公开角色对象析构后继续安全收尾。
- Mapping 在从站服务退出回调前保持有效。

`shared_ptr` 只用于确实跨异步生命周期的状态，不作为所有成员的默认选择。

## 13. 配置访问

串口配置只允许在 `Closed` 状态修改。

`open()`、`setOptions()` 和 `options()` 使用配置访问保护，避免与关闭线程同时
读写配置对象。通信期间配置保持不变。

配置失败时关闭文件描述符，不保留半配置状态。

## 14. 为什么没有继续增加设计模式

当前不需要：

- 主从站公共虚基类：组合传输对象已经足够复用。
- 每个功能码一个 Command 类：`ModbusRequest` + 通用事务已经足够。
- 每个状态一个派生类：当前状态数量和流程用枚举与成员函数更直观。
- 复杂工厂：直接构造具体角色已经表达用途。
- CRTP 主从站模板：主要难点是运行时状态和生命周期，不是静态分派。
- 通用 Operation 调度器：已被证明会扩大“已投递但未启动”的取消边界。

设计模式不是目标。当前采用的是几项基础思想：

- 单一职责。
- 组合优于继承。
- 状态机。
- strand 状态封闭。
- 纯函数处理协议。
- RAII 和明确所有权。
- 异步完成契约。

## 15. 修改带来的管理收益

### 15.1 修改范围更明确

| 要修改的内容 | 对应文件 |
| --- | --- |
| CRC、长度、响应匹配 | `detail/rtuCodec.cpp` |
| 串口、定时器、帧间等待 | `detail/serialTransport.cpp` |
| 主站事务和重试 | `rtuMaster.cpp` |
| 从站地址、广播、Mapping | `rtuSlave.cpp` |
| 手动收发 | `modbusSerial.cpp` |

### 15.2 异常路径可单独验证

取消、关闭、帧间等待和半帧接收可以在传输层测试，不需要构造完整主从站业务。

### 15.3 接口约束更明确

“什么时候可以打开”、“什么时候可以修改配置”、“关闭何时真正完成”都有唯一答案，
不再依赖调用者猜测 `busy()` 或 `isOpen()` 的组合含义。

### 15.4 回归测试更有针对性

当前测试覆盖：

- 事件循环启动前取消，不产生物理写。
- 从站停止后可立即重启。
- `frameGap` 作用于正常响应。
- 手动请求帧与响应帧按类型解析。
- 跨线程析构时完成回调恰好一次。
- 关闭完成后串口状态为 `Closed`，并可在完成回调中重新打开。

### 15.5 后续扩展成本更低

新增功能码通常只需要：

1. 构造 `ModbusRequest`。
2. 复用主站通用事务。
3. 在 codec 中补充响应匹配规则。

不需要复制一套串口流程，也不需要新增 Operation 子类。

## 16. 接口约定

- 一个串口实例只承担手动、主站或从站中的一个角色。
- 主站只排完整事务。
- 从站只运行一个服务循环。
- 串口配置只在 `Closed` 状态修改。
- 底层同一时间只有一个读或写。
- 完成回调异步派发，不应抛出异常。
- `cancel()` 取消当前事务或服务，但保持串口打开。
- `asyncClose()` 在完成回调前完成角色收尾并关闭串口。
- `io_context` 必须活到异步完成和关闭回调结束。

## 17. 验证边界

伪终端测试可以验证软件状态、字节顺序和定时逻辑，但不能证明：

- 真实 RS485 电平与 RTS 接线。
- USB-RS485 芯片内部缓存何时排空。
- 物理线路的 t1.5 / t3.5 严格时序。
- 所有驱动的 ioctl 行为。

ThreadSanitizer 可以编译，但当前运行环境在启动时报告
`unexpected memory mapping`，因此不能据此声称多线程压力验证完成。
